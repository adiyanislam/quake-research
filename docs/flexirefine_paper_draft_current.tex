\begin{abstract}
% ============================================================
% [CONFIRMED] 38-45% maintenance reduction, recall >= 0.90, overhead < 5%
% [CONFIRMED] Static Faiss-IVF is over 4x slower total runtime

Dynamic vector search systems must maintain high recall and low query
latency under continuous inserts, deletes, and shifting access patterns.
Existing adaptive partitioned indexes improve on static approaches but
expose only limited control over the tradeoff between maintenance cost,
search quality, and total runtime: maintenance is typically either fully
enabled or fully disabled, with few principled options in between.

We present \system, a control-plane framework that treats post-split
partition refinement as a tunable resource allocation problem.
Rather than refining all candidate partitions after each structural
change, \system ranks candidates using a joint importance--staleness
score that combines recent query hit counts with mutation-based staleness.
The score family $S_{\beta,\gamma}(p) = (h_p + 1)^\beta D(p)^\gamma$
subsumes raw, density-normalized, and exponent-weighted staleness signals,
giving users a principled and interpretable control surface.

We implement \system on top of a dynamic partitioned vector index and
evaluate on a SIFT1M dynamic workload with inserts, deletes, and queries,
reporting mean\,$\pm$\,std across three independent workload seeds.
\textbf{Score-based selective refinement reduces maintenance by 38--45\%
while preserving mean recall above 0.90, with total runtime overhead
below 5\%.}
For comparison, a static Faiss-IVF index that performs no maintenance
pays over 4$\times$ higher total runtime and fails the 0.90 recall target
on one of three seeds, demonstrating that dynamic maintenance is necessary
under realistic insert/delete workloads.
\end{abstract}

\section{Introduction}
\label{sec:intro}
% ============================================================

Vector search is a core primitive in retrieval-augmented generation,
recommendation systems, semantic search, and embedding-based
personalization~\cite{lewis2020rag, radford2021clip}.
These applications store large collections of high-dimensional vectors
and answer approximate nearest-neighbor queries under strict latency and
recall requirements. In practice, the underlying data is rarely static:
new embeddings arrive continuously, stale vectors are deleted, and query
distributions shift with user interests. These dynamics make vector
indexing significantly harder than static approximate nearest-neighbor
search~\cite{malkov2020, jayaram2019}.

Existing systems address this tension unevenly. Graph-based indexes such
as HNSW~\cite{malkov2020} and DiskANN~\cite{jayaram2019} achieve strong
search quality in read-heavy settings but degrade under high-churn
workloads, as frequent insertions and deletions can corrupt graph
structure. Partitioned indexes such as Faiss-IVF~\cite{johnson2021} and
ScaNN~\cite{guo2020} support localized inserts and deletes but suffer
from partition imbalance and centroid drift if maintenance is neglected.
Recent adaptive systems~\cite{todo-quake, zhang2023spfresh} show that
cost-model-driven maintenance can substantially improve dynamic
partitioned search. However, even these systems expose only a narrow
set of operating points: maintenance is either fully enabled or fully
disabled, with few principled options in between.

The deeper limitation is a \emph{control} problem. Different deployments
have fundamentally different tradeoff requirements:
\begin{itemize}[leftmargin=*]
  \item A retrieval-augmented generation pipeline may require recall
    above 0.90 and accept higher maintenance overhead.
  \item A high-ingestion streaming system may want aggressive maintenance
    reduction even at a modest recall penalty.
  \item A latency-sensitive recommendation service cares most about
    stable per-query latency.
  \item A balanced deployment wants recall near target, lower
    maintenance, and no increase in total runtime.
\end{itemize}
A single fixed policy cannot serve all of these needs. What is needed is
a \emph{controllable maintenance system} that makes these tradeoffs
explicit, rather than hiding them behind internal defaults.

This paper presents \system, a control-plane framework for dynamic
partitioned vector index maintenance that focuses on
\emph{partition refinement}---the operation that repairs local
partition quality by running K-means on the neighbors of recently
split partitions. Refinement is important: disabling it cuts maintenance
time by roughly $14\times$ but drops recall by approximately 3 points
in our experiments. This makes refinement a natural control point: costly
enough to matter, important enough that removing it blindly is unsafe.

\system treats refinement as a resource allocation problem. Given a
maintenance budget, the system ranks candidate partitions by a score
that jointly estimates workload importance and structural staleness, then
refines only the top-ranked subset. The score family:
\begin{equation}
  S_{\beta,\gamma}(p) = (h_p + 1)^\beta D(p)^\gamma
\end{equation}
where $h_p$ counts recent query hits and $D(p)$ estimates staleness,
subsumes raw mutation counts, density-normalized mutation rates, and
exponent-weighted variants as special cases. No single $(\beta,\gamma)$
pair is universally optimal; the family is a tunable control surface
that users can select from based on application priorities.

This paper makes the following contributions:

\begin{enumerate}[leftmargin=*, label=\textbf{C\arabic*.}]
  \item \textbf{Control-plane problem identification.}
    We identify the missing flexibility in dynamic vector index
    maintenance: existing systems lack principled control over the
    tradeoff between recall, maintenance cost, and total runtime.
    We frame this as a resource allocation problem over partition
    refinement.

  \item \textbf{Score-based selective refinement design.}
    We design \system, a modular refinement-control framework built
    around a joint importance--staleness scoring signal. We define the
    general score family $S_{\beta,\gamma}(p)$, analyze its properties,
    and show that density-normalized staleness provides a more stable
    signal than raw mutation count.

  \item \textbf{Full implementation and infrastructure.}
    We implement \system in C++ and Python on top of a dynamic
    partitioned vector index. The implementation includes per-partition
    mutation tracking, sliding-window hit tracking, score-based
    candidate selection, and a multi-seed evaluation infrastructure that
    reports mean\,$\pm$\,std to account for K-means non-determinism.

  \item \textbf{Empirical evaluation with external baselines.}
    We evaluate \system on dynamic SIFT1M workloads across three seeds
    and show 38--45\% maintenance reduction with mean recall above 0.90
    and total runtime overhead below 5\%. For comparison, a static
    Faiss-IVF index (no dynamic maintenance) pays over $4\times$ higher
    total runtime and fails the recall target on one of three seeds.
\end{enumerate}

\subsection{Vector Search Indexes}

Vector search organizes high-dimensional vectors for approximate
nearest-neighbor retrieval.
Graph-based indexes navigate proximity graphs at query time.
HNSW~\cite{malkov2020} builds a multi-layer navigable small world
graph and achieves strong recall--latency tradeoffs in static settings.
DiskANN~\cite{jayaram2019} extends graph-based search to disk-resident
datasets through a Vamana graph with sector-granular I/O.
These indexes are competitive for read-heavy workloads but can be
expensive to maintain under frequent updates.

Partitioned (IVF-style) indexes cluster vectors into cells and scan a
subset of cells per query.
Faiss~\cite{johnson2021} provides a comprehensive library of flat, IVF,
and product-quantization~\cite{jegou2011pq} indexes.
ScaNN~\cite{guo2020} uses anisotropic vector quantization for improved
recall at low nprobe.
SPANN~\cite{chen2021spann} combines graph routing with inverted-list
scanning for billion-scale search.
These approaches are attractive for dynamic workloads due to localized
insert/delete operations.
\system builds on the partitioned-index design space and adds a
refinement-control layer on top of it.

\subsection{Dynamic and Streaming Vector Search}

Static indexes must be periodically rebuilt or updated to handle
evolving data. Several systems address vector search under continuous
updates.

SPFresh~\cite{zhang2023spfresh} performs incremental in-place updates
on billion-scale IVF indexes through size-based partition splitting and
reassignment without centroid repair, avoiding expensive global rebuilds.
\quake~\cite{todo-quake} uses a cost-model-driven maintenance policy to
decide when to split, merge, or delete partitions based on estimated
scan-latency impact, and runs local K-means refinement after splits.
DeDrift~\cite{todo-dedrift} targets concept drift by monitoring
embedding distribution shifts and triggering selective index repair.
FreshDiskANN~\cite{todo-freshdiskann} extends graph-based indexing to
streaming inserts and deletes with bounded quality loss.

\system is complementary to all of these: rather than replacing
split/merge/delete logic, it controls how K-means refinement effort is
allocated after structural changes. LIRE-style maintenance
(size-based splits, reassignment only, no K-means) serves as a pending
baseline in our evaluation.

\subsection{Adaptive Query Processing and Index Maintenance}

Adapting execution based on observed workload is a long-standing idea
in data systems.
VBASE~\cite{xu2023vbase} unifies online vector similarity search with
relational queries through relaxed monotonicity, enabling adaptive
hybrid execution.
APS (from \quake) and LAET~\cite{todo-laet} adapt search-time behavior
by dynamically adjusting how many partitions are scanned to hit a recall
target.
Auncel~\cite{todo-auncel} targets fast approximate vector queries on
large unstructured datasets using learned termination conditions.

Database adaptive indexing and physical design tuning
use workload-driven feedback to selectively build and update index
structures.
\system applies the same principle at the maintenance layer: workload
hit counts feed directly into refinement allocation decisions.

\subsection{Vector Databases and Data Management Systems}

\section{Design of \system}
\label{sec:system}
% ============================================================

\subsection{System Model}

We consider a dynamic partitioned vector index. The index stores vectors
in partitions, each represented by a centroid. Queries search a subset
of partitions using approximate nearest-neighbor scan. Updates insert
or delete vectors. Maintenance periodically modifies the index
structure through splits, deletes, and refinements.

Let $P$ be the set of partitions. Each partition $p \in P$ has:
\begin{itemize}[leftmargin=*]
  \item size $|p|$ (number of resident vectors),
  \item centroid $c_p$,
  \item recent query-hit count $h_p$,
  \item mutation count $m_p$ (since last refinement),
  \item minimum distance to recent split centroids $d_p$.
\end{itemize}

\system operates during maintenance. When the underlying index decides
that one or more partitions should be split, \system controls the
refinement stage that follows those splits.

\subsection{Architecture Overview}

\system inserts a five-module refinement-control layer between split
decisions and refinement execution:

\begin{enumerate}[leftmargin=*]
  \item \textbf{Candidate Generator.}
    Given newly split partition centroids $S$, retrieve the $r_f$
    nearest partition centroids from the parent index per split centroid.
    Deduplicate across split centroids by keeping minimum distance per
    candidate:
    $C = \bigcup_{s \in S} \mathrm{Nearest}_{r_f}(s, P)$,
    $d_p = \min_{s \in S} \|c_p - c_s\|$.

  \item \textbf{Metadata Tracker.}
    Maintain per-partition statistics: size, query hit count,
    mutation count, and distance to split centroids. Update after every
    insert, delete, and refinement cycle.

  \item \textbf{Scoring Engine.}
    Compute a refinement score for each candidate using a selectable
    function of hit count and staleness.

  \item \textbf{Budget Allocator.}
    Select a subset of candidates under a global top-$K$ budget,
    per-split budget, threshold, or hybrid policy.

  \item \textbf{Refinement Executor.}
    Apply local K-means refinement to selected partitions. Reset
    mutation counters for refined partitions.
\end{enumerate}

This architecture is intentionally modular. The underlying split/merge
and delete decisions remain unchanged; \system changes only which
partitions receive post-split quality repair.

\subsection{Problem Formulation}

After a set of splits, the candidate generator produces candidate set
$C$. A refinement policy $\pi$ selects a subset under budget $B$:
\begin{equation}
  \pi(C, B) \subseteq C, \quad |\pi(C, B)| \leq B
\end{equation}
The ideal policy minimizes a multi-objective:
\begin{equation}
  \pi^* = \arg\min_{\pi(C,B)}
    \bigl[\lambda_s T_s(\pi) + \lambda_m T_m(\pi)
          + \lambda_u T_u(\pi) - \lambda_r R(\pi)\bigr]
\end{equation}
where $T_s, T_m, T_u, R$ are search time, maintenance time, update
time, and recall. This is not solvable online because the effect of
refining a candidate on future recall is not known. \system approximates
utility through observable metadata.

\subsection{Candidate Generation}

The radius $r_f$ controls the spatial scope of repair. It is a
geometric candidate-generation parameter, not a ranking signal:
distance identifies which partitions are structurally affected but
does not measure workload importance.

\subsection{Metadata Tracking}

\textbf{Query hits.} For sliding window $W$ of recent queries:
\begin{equation}
  h_p = \sum_{q \in W} \mathbf{1}[p \in \mathrm{scanned}(q)]
  \label{eq:hits}
\end{equation}
Maintained in a circular buffer of size $|W|$. Reuses per-query
partition-scan data already recorded for adaptive partition scanning;
no additional query interception is needed.

\textbf{Mutation count.}
\begin{align}
  m_p &\leftarrow m_p + \Delta_p \quad \text{(on insert or delete)} \\
  m_p &\leftarrow 0 \quad \text{(after refinement of } p\text{)}
  \label{eq:mutations}
\end{align}
Newly split child partitions are seeded with $m_p = \max(1, |p|)$
to ensure they enter scoring as non-trivially stale.

\textbf{Density-normalized staleness.}
\begin{equation}
  \tilde{m}_p = \frac{m_p}{|p|}
  \label{eq:density}
\end{equation}
This estimates the mutation \emph{rate per resident vector}, which
approximates centroid displacement more accurately than absolute
mutation count: a large partition receiving 2000 inserts has a smaller
centroid shift per vector than a small partition receiving the same.

\subsection{Refinement Control Policies}

\subsubsection{Split-Threshold Tuning}
A partition is split when the predicted latency benefit exceeds threshold
$\tau_s$: $\Delta C_{\mathrm{split}} < -\tau_s$.
Higher $\tau_s$ reduces splits and therefore total refinement
opportunities. Split-threshold tuning alone cannot recover the recall
target (\S\ref{sec:eval_negative}).

\subsubsection{Refinement Radius and Iterations}
Radius $r_f$ bounds candidate set size; $i_f$ K-means iterations control
repair depth per refinement call. Both parameters set the scope of work
without controlling which partitions within that scope are most valuable
to refine.

\subsubsection{Size-Based and Distance-Based Filtering}
\begin{equation}
  S_{\mathrm{size}}(p) = \mathbf{1}[|p| \geq \tau_{\mathrm{size}}],
  \quad
  p \in \pi \iff d_p \leq \tau_d
\end{equation}
Neither signal captures workload importance or staleness. Both are
shown to fail in \S\ref{sec:eval_negative}.

\subsubsection{Global Top-$K$ Selection}
$\pi(C, K) = \mathrm{TopK}_{p \in C}\, S(p)$.
Controls maintenance budget directly. Requires a strong score to be
effective; without it, it simply refines fewer partitions.

\subsubsection{Per-Split Budgeting}
$\pi(C, b) = \bigcup_{s \in S} \mathrm{Top\text{-}b}(C_s)$.
Allocates $b$ slots per split centroid before the global union.
Fails to preserve recall because per-centroid caps block globally
high-value candidates (\S\ref{sec:eval_negative}).

\subsubsection{Hit-Based Refinement}
$S_{\mathrm{hit}}(p) = h_p$.
Prioritizes frequently queried partitions but ignores structural
degradation; insufficient alone.

\subsubsection{Hits-by-Mutations (Raw Staleness)}
\begin{equation}
  S_{\mathrm{raw}}(p) = (h_p + 1)\, m_p
  \label{eq:raw_score}
\end{equation}
Selects partitions that are both important and stale.
The $+1$ smoothing ensures partitions with zero hits but high mutations
receive a non-trivial score.

\subsubsection{Hits-by-Density (Density-Normalized Staleness)}
\begin{equation}
  S_{\mathrm{density}}(p) = (h_p + 1)\, \frac{m_p}{|p|}
  \label{eq:density_score}
\end{equation}
Replaces raw mutation count with mutation density (Eq.~\ref{eq:density}).
Empirically achieves lower maintenance variance than raw staleness at
comparable recall levels (\S\ref{sec:eval_seeds}).

\section{Theoretical Analysis}
\label{sec:theory}
% ============================================================

\subsection{Refinement Utility}

Let the expected benefit of refining partition $p$ be:
\begin{equation}
  B(p) = \Delta R(p) - \alpha \Delta T_s(p)
\end{equation}
where $\Delta R(p)$ is the expected recall improvement and
$\Delta T_s(p)$ is the expected search-time reduction.
Refinement cost is $K(p) = T_{\mathrm{refine}}(p)$.
Net utility:
\begin{equation}
  U(p) = B(p) - \beta K(p)
\end{equation}
Since $B(p)$ is not directly observable online, \system approximates
it using the measurable signals $h_p$, $m_p$, $|p|$, and $d_p$.

\subsection{Importance and Staleness}

\textbf{Partition importance} estimates how much future queries depend
on partition $p$:
\begin{equation}
  I(p) = f_h(h_p)
\end{equation}
Examples: $f_h = h_p$ (linear), $f_h = \log(1+h_p)$ (diminishing
returns), $f_h = \sigma(\alpha h_p)$ (sigmoid saturation).
Diminishing-return transforms model the observation that extremely hot
partitions should not consume all refinement budget.

\textbf{Partition staleness} estimates structural degradation:
\begin{equation}
  D(p) = f_m(m_p)
\end{equation}
Staleness transforms and their physical motivations:
\begin{equation}
  f_m(m_p) = m_p
  \quad \text{(raw: absolute mutations)}
\end{equation}
\begin{equation}
  f_m(m_p) = \frac{m_p}{|p|}
  \quad \text{(density: mutations per resident vector,}
  \text{ approximates centroid drift rate)}
\end{equation}
\begin{equation}
  f_m(m_p) = \sqrt{m_p}
  \quad \text{(sqrt: sublinear growth of staleness signal)}
\end{equation}
\begin{equation}
  f_m(m_p) = \log(1+m_p)
  \quad \text{(log: strong compression of high-mutation outliers)}
\end{equation}
These transforms reflect different assumptions about how centroid
displacement accumulates as a function of update count and partition
size.

\subsection{General Score Family}

The general multiplicative family unifies all of the above:
\begin{equation}
  S_{\beta,\gamma}(p) = (h_p + \epsilon)^\beta\, D(p)^\gamma
  \label{eq:general}
\end{equation}
where:
\begin{itemize}[leftmargin=*]
  \item $\beta \geq 0$ controls importance sensitivity: $\beta = 1$ is
    linear, $\beta < 1$ applies diminishing returns to hit counts,
    $\beta > 1$ amplifies hot partitions.
  \item $\gamma \geq 0$ controls staleness sensitivity: $\gamma = 1$ is
    linear, $\gamma < 1$ compresses high-staleness outliers.
  \item $\epsilon > 0$ smooths sparse hit counts.
  \item $D(p)$ can be any staleness transform.
\end{itemize}

Special cases:
\begin{center}\small
\begin{tabular}{llll}
  \toprule
  $\beta$ & $\gamma$ & $D(p)$ & Policy name \\ \midrule
  1 & 0 & any & Hit-only \\
  0 & 1 & $m_p$ & Mutation-only \\
  1 & 1 & $m_p$ & Hits-by-mutations (raw) \\
  1 & 1 & $m_p/|p|$ & Density-Linear \\
  0.5 & 1 & $m_p/|p|$ & SqrtHits-density \\
  1 & 0.5 & $m_p/|p|$ & SqrtMut-density \\
  0.5 & 0.5 & $m_p/|p|$ & SqrtBoth-density \\
  \bottomrule
\end{tabular}
\end{center}

\textbf{Important.} No single $(\beta, \gamma)$ pair is claimed as
universally optimal. The family provides a tunable control surface.
Empirical results (\S\ref{sec:eval_main}--\S\ref{sec:eval_seeds}) show
that all density-normalized configurations with linear or sublinear
importance ($\beta \leq 1$) achieve the recall target with 38--45\%
maintenance reduction. Super-linear importance amplification
($\beta > 1$) consistently degrades recall.

An additive feature model is also expressible:
\begin{equation}
  S(p) = w_h \phi(h_p) + w_m \psi(m_p) + w_d \chi(d_p) + w_s \eta(|p|)
\end{equation}

\subsection{Properties}

\textbf{Property 1 (Budget Monotonicity).}
For fixed $C$ and $S$: $B_1 \leq B_2 \Rightarrow
\mathrm{TopK}(C, B_1) \subseteq \mathrm{TopK}(C, B_2)$.
Budget is a monotone control knob; increasing $B$ cannot reduce the
number of refined candidates.

\textbf{Property 2 (Refinement Cost Upper Bound).}
With $\leq B$ selected candidates of maximum size $s_{\max}$, dimension
$d$, and $i_f$ refinement iterations:
$T_{\mathrm{refine}} = O(B \cdot i_f \cdot s_{\max} \cdot d)$.
Worst-case refinement work is bounded by $B$ and $i_f$ independently.

\textbf{Property 3 (Score Approximates Refinement Return).}
If expected benefit increases monotonically with both $I(p)$ and $D(p)$,
then $S(p) = I(p) D(p)$ is largest exactly where both importance and
staleness are large. The product suppresses candidates that are hot but
stable (large $I$, small $D$) or stale but irrelevant (large $D$,
small $I$).

\section{System Implementation}
\label{sec:implementation}
% ============================================================

\subsection{Code Structure}

\system is implemented as targeted modifications to four components of
a dynamic partitioned vector index:

\begin{itemize}[leftmargin=*]
  \item \textbf{Maintenance policy} (\texttt{maintenance\_policies.cpp}):
    per-split candidate ranking, scoring, budget selection, and
    selective refinement execution.
  \item \textbf{Partition manager} (\texttt{partition\_manager.cpp}):
    per-partition mutation counter; incremented on add/remove, reset
    on refinement. A stale-partition guard filters candidate IDs that
    may have been deleted between the parent-index search and the
    refinement call.
  \item \textbf{Parameter struct} (\texttt{common.h}):
    \texttt{MaintenancePolicyParams} with all tunable fields at
    backward-compatible defaults.
  \item \textbf{Python bindings} (\texttt{wrap.cpp}):
    exposes all parameters to Python and YAML configuration.
\end{itemize}

\textbf{Libraries.}
The implementation uses C++17, PyTorch/LibTorch (tensor operations,
K-means clustering), Faiss (inverted-list storage, flat index for
parent centroid lookup), and pybind11 (Python/C++ bindings).

All parameters default to values that reproduce prior behavior:

  \item \texttt{refinement\_size\_threshold} (int, $-1$)
  \item \texttt{refinement\_distance\_threshold} (float, $-1$)
  \item \texttt{refinement\_top\_k\_hits} (int, $-1$)
  \item \texttt{refinement\_top\_k\_score} (int, $-1$)
  \item \texttt{refinement\_normalize\_mutations} (bool, \texttt{false})
  \item \texttt{refinement\_score\_beta} (double, 1.0)
  \item \texttt{refinement\_score\_gamma} (double, 1.0)
\end{itemize}

With all defaults, the score is $(h_p+1) \times m_p$,
numerically identical to the original formula.

\subsection{Selective Refinement Pipeline}

\begin{enumerate}[leftmargin=*]
  \item Split partitions produced by the base maintenance policy.
  \item Retrieve $r_f$ nearest neighbor centroids per split centroid.
  \item Apply per-split cap: sort by distance, truncate.
  \item Union into global min-distance map; filter stale IDs.
  \item Apply optional distance and size filters.
  \item Compute $S_{\beta,\gamma}(p)$ for each candidate.
  \item Select top-$K$ candidates.
  \item Run K-means refinement on selected candidates.
  \item Reset mutation counters for refined partitions.
\end{enumerate}

\subsection{Multi-Seed Evaluation Infrastructure}

To account for K-means non-determinism in refinement,
all primary results are reported as mean\,$\pm$\,std across three
independent workload seeds.
The experiment runner (\texttt{run.py}) accepts a
\texttt{seeds:~[s1, s2, s3]} list in the YAML configuration, generates
a separate workload per seed in \texttt{results/seed\_{s}/}, and after
all seeds complete, aggregates into
\texttt{multiseed\_summary.csv} and \texttt{multiseed\_summary.md}
with per-metric mean and standard deviation. All per-seed plots and
per-seed summary tables are also preserved.

\subsection{Evaluator Compatibility for Non-Quake Baselines}

The \texttt{WorkloadEvaluator} was extended to support non-Quake
index wrappers. Two issues were fixed:
(1)~\texttt{parent\_info} in \texttt{SearchTimingInfo} is
\texttt{None} for non-Quake indexes; the timing loop now guards
this with an existence check.
(2)~\texttt{maintenance()} returns \texttt{None} for static indexes
(Faiss-IVF); the evaluator null-checks the return value and records
zero maintenance cost.
Both fixes are backward-compatible: existing Quake configs are
unaffected.

\textbf{LIRE-style baseline status.}
We attempted to evaluate a LIRE-style baseline (size-based splits,
$\texttt{max\_partition\_size}=2000$, no K-means refinement) on the
full dynamic workload. The baseline encountered crashes during
mixed insert/delete sequences due to an interaction between
maintenance-triggered partition deletions and the workload generator's
resident-set tracking: when maintenance deletes a small undersize
partition without reassigning its vectors, the workload's resident set
diverges from the actual index state. A stale-partition guard and
a \texttt{min\_partition\_size=0} configuration were applied to prevent
partition-deletion events; the baseline is currently progressing
through the smoke test. Results will be added once confirmed.
\todo{Replace with confirmed 3-seed LIRE results once the delete-after-partition-deletion stability issue is fully resolved.}

\subsection{Engineering Considerations}

\begin{itemize}[leftmargin=*]
  \item Candidate scoring is $O(|C|)$ in the local neighborhood,
    not over all partitions.
  \item Hit counts reuse existing per-query scan data; no new
    query interception is needed.
  \item Mutation counters are lightweight 64-bit integer fields.
  \item All parameters are YAML-configurable with backward-compatible
    defaults.
\end{itemize}

\subsection{Score-Based Refinement Reduces Maintenance by 38--45\%}
\label{sec:eval_main}
% RQ1: does FlexiRefine reduce maintenance while preserving recall?
% ─────────────────────────────────────────────────────────────────────────────

\textbf{Refinement dominates maintenance cost.}
Disabling refinement (Quake-NoRefine) cuts maintenance from
103,926\,ms to 7,263\,ms ($14\times$) but drops recall from 0.909
to 0.879 (\textit{single-run, seed 9299}).
Disabling the cost-based rejection mechanism collapses recall to 0.768.
Refinement is the dominant maintenance cost and removing it blindly
is unsafe. Selective refinement---spending maintenance budget only
where it matters---is the natural solution.

hyperparameter-level claims.

\subsection{Coverage-Only Budgeting Fails to Preserve Recall}
\label{sec:eval_negative}
% RQ2: are score-based policies better than naive/coverage-only policies?
% ─────────────────────────────────────────────────────────────────────────────

\textbf{Split-threshold tuning.}
Recall stays below 0.90 regardless of threshold (\textit{single-run}).
Reducing split frequency reduces maintenance aggressively but does not
substitute for post-split quality repair. Selected results:
threshold 240\,ns gives maintenance 5,222\,ms, recall 0.8860.

\textbf{Global budget cap without value ranking.}
Applying a global top-$K$ cap without a scoring signal refines fewer
partitions, not better ones. Top-20 gives maintenance 29,363\,ms,
recall 0.8965 (\textit{single-run}). No cap value reaches 0.90.

\textbf{Per-split coverage budgeting (corrected post bug-fix).}
\superseded{Earlier numbers (PerSplit3-Top10 maintain 21,584,
recall 0.8903) were from a code defect in which
\texttt{refinement\_candidates\_per\_split} was not applied;
corrected in commit \texttt{ea4de23}.}

Per-split budgeting allocates $b$ candidate slots per split centroid
before the global union. After the correctness fix, no per-split
configuration reaches recall 0.90. Best result: PerSplit5-Top20/Top30 at
0.8945 versus global unranked refinement (RefineAll) at 0.9039.

The failure is structural: per-centroid caps block globally high-value
candidates when split centroids are spatially close and their
neighborhoods overlap. Local coverage guarantees do not substitute for
a global importance--staleness ranking signal.

\textbf{Summary.}
Size-only, distance-only, budget-without-ranking, per-split coverage,
hit-only, and $\beta>1$ policies all fail to reach 0.90 recall while
reducing maintenance. The consistent failure mode is prioritizing fewer
partitions without identifying the right ones.

\subsection{Policy Recommendations for Different User Priorities}
\label{sec:eval_recommendations}
% RQ5: which operating point should users choose?
% ─────────────────────────────────────────────────────────────────────────────

\begin{itemize}[leftmargin=*]
  \item \textbf{Recall-critical.}
    Use \textbf{Quake full refinement}.
    Mean recall 0.9118, lowest recall variance ($\pm$0.0134).
    Accept full maintenance overhead to guarantee recall.

  \item \textbf{Maintenance-constrained.}
    Use \textbf{Score50-Raw-Linear}: $S(p) = (h_p+1)\,m_p$, $K=50$.
    Mean maintenance 36,620\,ms ($-45.9\%$), recall 0.9017.
    Caveat: higher maintenance variance (CV=24.1\%).

  \item \textbf{Balanced.}
    Use \textbf{D70-B0.5-G0.5}: $S(p) = (h_p+1)^{0.5}(m_p/|p|)^{0.5}$,
    $K=70$.
    Best combined tradeoff: $-39.5\%$ maintenance, recall 0.9064,
    total overhead $+2.2\%$, lowest maintenance std (CV=10.9\%).

  \item \textbf{Simplicity and predictability.}
    Use \textbf{Density70-Linear}: $S(p) = (h_p+1)(m_p/|p|)$, $K=70$.
    Simplest density formulation, lowest maintenance CV (12.2\%),
    competitive recall (0.9033), $+2.9\%$ total overhead.
    Recommended default for deployments that prioritize
    predictable behavior over absolute minimum maintenance.

  \item \textbf{No-maintenance / static IVF.}
    \textbf{Not recommended} for dynamic insert/delete workloads.
    Faiss-IVF is $4.25\times$ slower in total runtime and fails the
    0.90 recall target on one of three seeds.
    Consider static IVF only for truly static datasets or
    predominantly read-only workloads where update simplicity
    matters more than search time and recall stability.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}
% ============================================================

Dynamic vector indexing systems should expose maintenance as a
controllable resource rather than a fixed internal policy.
\system demonstrates this by framing post-split partition refinement
as a resource allocation problem: rather than refining all candidates
after every split, it ranks candidates by a joint importance--staleness
score and refines only the top-ranked subset.
The key result, confirmed across three independent workload seeds,
is that score-based selective refinement reduces maintenance by
38--45\% while preserving mean recall above 0.90 with total runtime
overhead below 5\%, whereas a static Faiss-IVF index that forgoes
maintenance entirely is over $4\times$ slower in total runtime and
unreliable in recall across seeds.
Naive alternatives---size-only, distance-only, per-split coverage, and
budget-without-ranking policies---consistently fail to preserve the
recall target, confirming that a joint workload-importance and
structural-staleness signal is necessary.
We argue that \system's principal contribution is not a specific
hyperparameter setting but a \emph{control plane}: a principled,
configurable, and interpretable layer that makes the
recall--maintenance--latency tradeoff explicit and tunable for
diverse deployment priorities.

\subsection{Limitations and Discussion}

\textbf{Run variance.}
K-means refinement uses stochastic centroid initialization.
Over a 1000-operation dynamic workload, early-cycle randomness compounds
into meaningful divergence: maintenance cost CVs range from 10\% to
34\% across three seeds, and recall standard deviations are $\pm$0.015--0.022.
This motivates mean\,$\pm$\,std reporting and policy-class claims rather
than hyperparameter-level comparisons.

\textbf{Hyperparameter stability.}
The exact ranking within the score-based policy class (e.g., whether
$\beta=0.5$ or $\beta=1.0$ is better) is not stable at $n=3$ seeds.
At least $n=5$ seeds or deterministic K-means seeding are needed before
specific $(\beta, \gamma)$ values can be recommended conclusively.

\textbf{Scope.}
All confirmed results use SIFT1M with a 30/20/50 insert/delete/query
mix. Generalization to larger datasets (SIFT10M, MSTuring) and different
workload distributions requires further evaluation.

\textbf{Baseline completeness.}
Faiss-IVF is confirmed. A LIRE-style baseline (dynamic splits without
K-means) is under evaluation; preliminary runs encountered a
delete-after-partition-deletion instability that is being fixed.
Graph-based baselines (HNSW, ScaNN) are planned.

\subsection{Future Work}

\begin{enumerate}[leftmargin=*]
  \item \textbf{LIRE and graph baselines.}
    Complete the LIRE-style 3-seed comparison and add HNSW/ScaNN
    baselines to answer whether the FlexiRefine recall--runtime
    tradeoff is competitive with non-IVF approaches.

  \item \textbf{More seeds and deterministic K-means.}
    Extend to $n=5$ seeds (add 1337 and 2024). Alternatively, expose
    a K-means random seed in \texttt{refine\_partitions()} to enable
    fully reproducible experiments.

  \item \textbf{Larger workloads.}
    Evaluate on SIFT10M and MSTuring-10M to test generalization.

  \item \textbf{Adaptive budget control.}
    Adjust top-$K$ dynamically based on observed recall drift,
    targeting a recall threshold rather than a fixed candidate count.

  \item \textbf{Score-family fine-tuning.}
    With $\beta=1.0$ fixed, sweep $\gamma \in \{0.25, 0.5, 0.75, 1.0\}$
    to locate the optimal staleness exponent more precisely.
\end{enumerate}
